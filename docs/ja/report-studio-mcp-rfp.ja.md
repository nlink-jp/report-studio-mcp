# RFP: report-studio-mcp

> Generated: 2026-11-03
> Revised: 2026-11-03（独立検証の指摘を反映）
> Status: Draft

## 1. Problem Statement

gem-agent・lagent で行った調査の結果を、人に渡せる体裁の文書にする手段がない。現状は Markdown の
応答をそのまま渡すか、pandoc やブラウザ印刷で手作業で整形しており、グラフや構成図を入れるのは
さらに手間がかかる。report-studio-mcp は、エージェントが書いたレポート原稿（文章、グラフのデータ、
構成図の定義）を受け取り、組版した PDF と編集可能な Word 文書（.docx）を作業ディレクトリに出力する
MCP サーバである。外部サービスやブラウザに頼らず、macOS の機能だけで動く。当面の利用者は運用者本人、
呼び出し側は gem-agent と lagent。他の MCP クライアントは、作業ディレクトリと原稿を書く経路を実測して
から加える。

## 2. Functional Specification

### Commands / API Surface

| ツール | 役割 |
|---|---|
| `get_usage` | 使い方の全体: 受け付ける Markdown の範囲、` ```chart ` の JSON 仕様、プロファイルの指定、上限、エラー・警告の一覧（安定した `code` と対処） |
| `render` | 作業ディレクトリ内の原稿ファイルから PDF・.docx を出力する。同期で返す |

作業領域の一覧・中身を見るツールは置かない（image-forge・voice-studio・video-studio と同じ。作業領域の
名前空間は MCP サーバ間で共有されており、他サーバの作業領域を列挙する理由が無い）。検証専用のツールも
置かない。原稿の誤りは `render` が行番号つきで返す。

`render` の引数:

| 引数 | 内容 |
|---|---|
| `work_dir` | 必須・既定値なし（組織 ADR-021） |
| `workspace_id` | 出力先の作業領域 |
| `source` | 原稿のパス（`work_dir` からの相対） |
| `formats` | `pdf` / `docx`。既定は両方 |
| `profile` | プロファイル名。省略時は front matter、それも無ければ `standard` |
| `max_warnings` | 返す警告の件数。既定値を超えた分は件数だけ返すので、要るときは引き上げて取り直せる |

`render` の戻り値: `work_dir`、出力ごとの `path`（相対）と `abs_path`（組織 ADR-021 §6）、ページ数（PDF）、
警告の一覧（行番号・`code`・内容）と総件数、超過した件数。

`initialize` の instructions で `work_dir` の契約を名乗る（既存の作業ディレクトリ系サーバと同じ）。

### Input / Output

**入力: 普通の Markdown**

準拠する仕様（版は Phase 0 で固定した。CommonMark 0.31.2、GFM 0.29-gfm、脚注と注記は GitHub Docs、
.docx は ECMA-376 第 5 版の Transitional — 出典と参照日は [phase0-criteria.ja.md](phase0-criteria.ja.md) の P0-5）:

- 本文: CommonMark 仕様。正しさは同版の公式の例（約 650 件）を試験データにして確かめる。
- GitHub の拡張（表、取り消し線、チェックリスト、自動リンク）: GFM 仕様。
- 脚注と注記ブロック（`> [!NOTE]` / `> [!WARNING]` など）: GFM 仕様には無いので、GitHub Docs の記述を
  出典として記録し、そこから試験を起こす。
- front matter: 先頭の `---` 行で囲んだ `key: value` の 1 段の並びに限る（入れ子・配列なし）。認める
  キーは題名、副題、作成者、日付、区分（例「社外秘」）、`profile`、表紙・目次の有無。すべて任意で、
  知らないキーは警告。無ければ最初の見出しを題名に使う。

原稿に書けるもの:

- ` ```chart ` ブロック: JSON でグラフの種類とデータを書く。種類は縦棒・横棒（グループ・積み上げ）、
  折れ線、散布図。描画はサーバが行い、モデルは描画コードを書かない。
- ` ```mermaid ` ブロック: mermaid-render が対応する図（flowchart、sequence、ER、state、gantt、pie、mindmap）。
- 画像 `![キャプション](相対パス)`: 原稿のあるディレクトリから辿る。辿れる範囲は `work_dir` の中だけ。
  data-toolbox-mcp が別の作業領域に書いた PNG も取り込める。形式は中身で判定し、PNG と JPEG に限る。
  URL からの取得はしない。
- リンク: クリックできるのは `http`・`https`・`mailto` だけ。それ以外のスキームは文字として出し、警告する。
  無害化された URL（`hxxp://`、`[.]` など）は元に戻さず、そのまま文字として出す。

**エラーと警告の線引き**

エラー（出力しない）は「出力が間違ったものになる」場合だけ:

- chart の JSON が不正
- 画像が無い・読めない・`work_dir` の外・形式が PNG/JPEG でない・上限超過
- 原稿や表などが上限を超える（下の「上限」）

それ以外は警告にとどめて出力する:

- mermaid の図が描けない（`SyntaxError`・`UnsupportedType`・`UnsupportedConstruct`・`LayoutFault`）:
  mermaid-render の約束どおり、図の代わりにソースをコードブロックとして載せる。印刷用の倍率で画素数の
  上限を超える図は、倍率を下げて描く。
- 生の HTML は文字として表示。4 段目以降の見出しは 3 段目の見た目。
- 幅の広い表は文字を下限まで小さくしてから、セル内で折り返す。改行できない長い行（コード、URL）は
  強制的に折り返す。
- .docx（XML）に入れられない制御文字は取り除く。

**上限**

原稿のバイト数、ページ数、表の行数・列数、グラフのデータ点数、画像の数・寸法・バイト数・総量、出力の
総量に上限を設ける。画像は寸法を先に読み、上限内のものだけをデコードする。初期値は Phase 0 で最悪の
場合の所要時間を測って決め、gem-agent の呼び出しの既定の打ち切り（60 秒）に十分な余裕を残す（初期値と
測定は [phase0-criteria.ja.md](phase0-criteria.ja.md) の P0-4。費用はほぼ画像の画素数で決まるため、画像と
mermaid の図の画素数を一つの予算にまとめる）。
mermaid-render の上限（ノード数など）はそのまま引き継ぐ。

**出力**

- 原稿の `work_dir` からの相対パスを保ったまま、作業領域の `out/` の下に出す
  （例: `a/report.md` → `<作業領域>/out/a/report.pdf`）。別のディレクトリの同名の原稿が衝突しない。
- 置き方: すべて `os.Root`（作業ディレクトリ）越しに行う。一時名のファイルを新規作成（`O_EXCL`）して
  書き、最終名へ `rename` する。リンクを辿って外へ書くことはない。
- PDF: 本文はフォントのサブセットを埋め込み、数値のグラフはベクター、mermaid の図は印刷に十分な解像度の
  ラスター画像。リンクはクリック可能（上のスキームのみ）。
- .docx: プロファイルを Word のスタイル（見出し・本文・表・注記など）に写すので、受け取った側が Word で
  体裁を直せる。グラフは PNG。目次は Word の目次フィールド。準拠は Office Open XML（ECMA-376）。版と
  形式（Word が書く Transitional）は Phase 0 で固定し記録する。
- メタデータ: PDF の文書情報・.docx の `core.xml`・画像の説明には、front matter の題名・作成者と
  キャプションだけを書く。絶対パス、ユーザー名、入力ファイル名は書かない（回帰テストで確かめる）。

### Configuration

設定ファイルは無くても動く。探す順は `$XDG_CONFIG_HOME/report-studio-mcp/config.toml` →
`~/.config/report-studio-mcp/config.toml` → `~/Library/Application Support/report-studio-mcp/config.toml`。
実際に読んだパスをログと `get_usage` に出す。知らないキーはエラーにする（厳格に読む）。

- `[server]`: ログの設定。
- `[profiles.<名前>]`: 出力プロファイル。`extends = "<同梱名>"` で同梱プロファイルを土台に一部だけ上書き。

プロファイルで変えられる項目: 用紙（A4 / Letter）と余白、本文・見出し・コードのフォント（インストール
済みの任意のフォント）、文字サイズと行間、色（見出し・強調・注記・グラフの配色）、ヘッダー・フッター
（題名、区分、ページ番号）、表紙・目次の有無、表紙のロゴ画像。mermaid の図の中の文字は、当面ヒラギノに
固定する（mermaid-render はフォントを Core Text とは別の仕組みで読み、読めない書体があるため）。

設定の誤り（存在しないフォントなど）でサーバを止めない。そのプロファイルを使う `render` が、原因を
名指したエラー（`code` つき）を返す。他のプロファイルは使える。

同梱プロファイル（バイナリに組み込み、書き換え不可）:

| 名前 | 用途 | 体裁 |
|---|---|---|
| `standard`（既定） | 普段の調査レポート | A4、ヒラギノ角ゴ、表紙・目次なし、フッターにページ番号 |
| `formal` | 社内向けの正式文書 | 表紙・目次あり、本文ヒラギノ明朝、ヘッダーに区分 |
| `compact` | 下書き・メモ | 余白・文字を小さくしページ数を抑える |

モデルはプロファイルを名前で選べるだけで、内容は運用者の設定ファイルが決める。

### External Dependencies

- macOS の Core Text・Core Graphics（cgo 経由）。OS が保守する部品。
- 自前のライブラリ: `nlink-jp/mermaid-render`、`nlink-jp/pathguard`。mermaid-render が持ち込む
  `golang.org/x/image`・`golang.org/x/text` は、mermaid-render で申告・承認済みの例外を引き継ぐ。
- TOML の読み込みは組織のライブラリ `nlink-jp/toml`（標準ライブラリのみ、TOML 1.1.0、既定で未知の
  キーをエラーにする）。Discussion Log 11 を参照。
- MCP の実装（JSON-RPC・stdio・ツール登録・構造化エラー・作業ディレクトリの解決）は、依存が
  pathguard だけの chrome-pilot-mcp から移植する。どのパッケージをどこから持ってきたかは AGENTS.md に
  記録する。
- 外部サービス・ネットワーク: なし。

## 3. Design Decisions

| 判断 | 理由 |
|---|---|
| スキルではなく Go の MCP サーバ | 既存 MCP サーバとビルド・署名・tap・リリースの手順が共通。mermaid-render を直接組み込める。claude.ai にアップロードしたスキルは Linux で動くため macOS の機能を使えない |
| PDF は Core Text・Core Graphics で組版 | Chrome に依存しない。禁則処理とフォントのサブセット埋め込みは OS が行う（試作で確認、Discussion Log 参照）。セキュリティ更新は OS 側で届く |
| 依存は増やさない | コミュニティ製の部品を採用しない組織方針（組織 ADR-024）。.docx の書き出し、Markdown と TOML の読み取りは自前 |
| グラフは 1 回描いて 2 形式に出す | PDF にはベクター、.docx には OS で PNG 化したものを入れる |
| エラーは「間違い」だけ | 書式を固定しすぎると、範囲外の書き方のたびに拒否と書き直しが起き使いにくい。描けない図はソースで代える。見た目の問題は人間に委ねる |
| 読み書きは `os.Root` 越し | 起動された MCP サーバはどのランタイムでも閉じ込められておらず（組織 ADR-021 §7）、作業ディレクトリはサンドボックス内から書ける。字面のパスを確かめてから開く方式は TOCTOU になる。pathguard は「決して触らない場所」の床であって閉じ込めではないので、`os.Root` の上に重ねて使う |
| 見た目はプロファイルで切り替え | 同梱 3 種＋`extends` による上書き。Word テンプレートの読み込みは複雑なので採らない |
| 書き方の案内の置き場所 | 道具としての使い方は `get_usage`。良いレポートの書き方と手順は別のサポート用スキル（skills-series、別 RFP）。パラメータやエラー表をスキルに書かない（ずれの源になる） |

**補完する既存ツール**: gem-agent・lagent（呼び出し側）、mermaid-render（図）、pathguard（床の判定）、
data-toolbox-mcp（分析グラフの画像）、incident-research などの調査スキル（清書の入力元）。

**範囲外**: Word テンプレートの読み込み、既存 PDF・.docx の編集、PowerPoint 出力、HTML 出力、
URL からの画像取得、縦書き、数式、PDF の暗号化・電子署名、PDF/A・タグ付き PDF、macOS 以外の OS、
gem-agent・lagent 以外の MCP クライアントへの対応表明（実測の後に加える）。

**受け入れた残余**:

- mermaid の図は PDF の中でラスター画像になる（mermaid-render の出力が画像のため）。印刷に十分な解像度で
  入れる。
- 図の中の文字はプロファイルのフォント指定に従わない（当面ヒラギノ固定）。

## 4. Development Plan

### Phase 0: 実機での確認（実装の前）

合格条件を先に書いてコミットしてから測る。不合格なら設計判断に戻る。

1. Go から cgo で Core Text・Core Graphics を呼び、Python 試作と同じくフォントのサブセット埋め込みと
   禁則処理ができること。あわせて、これらのフレームワークが stdout に書くかを確かめる（書くなら fd の
   段階で JSON-RPC の stdout を隔離する）。cgo でリンクしたバイナリの対応 OS の下限（`LC_BUILD_VERSION`
   の minos）を明示して確かめる。
2. 手書きの最小の .docx（見出しスタイル、表、画像、脚注、目次フィールド）が Mac 版の Word と Pages の
   両方で内容を欠かさずに開けること。これは人が開いて確かめる（`textutil` は Word とは別の読み手）。
3. mermaid の図を PDF に埋め込んだときのファイルサイズと解像度、印刷用の倍率で画素数の上限に当たる図の
   割合。
4. 最悪の場合の原稿（上限いっぱいの表・画像・ページ数）の所要時間を測り、上限の初期値を決める。
5. 準拠する仕様の版（CommonMark、GFM、ECMA-376）を固定し、脚注・注記の出典とともに記録する。

### Phase 1: Core（PDF を出せるところまで）

- MCP の骨組み: 組織 ADR-021 の作業ディレクトリ契約、`get_usage`、`render`、安定した `code`、
  スキーマの arch テスト。作業領域の管理は `CheckBeneath` を必須の引数に取る（組織 ADR-022 §5）。
- 読み書きの層: `os.Root`、pathguard の床の判定、通常ファイルだけを開く、一時名＋`rename` の置き方。
- Markdown の読み取り: CommonMark 公式の例を全件試験に。GitHub の拡張、脚注、注記、front matter。
- PDF の組版: 見出し、段落、リスト、表、コード、注記、画像、改ページ、ヘッダー・フッター、ページ番号、
  リンク、収まらない内容の扱い。
- グラフ（棒・折れ線・散布図）の描画、mermaid の図の組み込みと描けないときの代替。
- 上限の実装。同梱プロファイルは `standard` のみ。自前の TOML 読み取り（厳格）。

### Phase 2: Features（Word と見た目の設定）

- .docx の出力: プロファイルを Word のスタイルに、表・画像・脚注・目次フィールド、制御文字の除去。
- 設定ファイルのプロファイルと `extends`、同梱の `formal`・`compact`。
- 表紙と目次（PDF・.docx の両方）。

### Phase 3: Release

- `get_usage` の本文、README（日英）、AGENTS.md、CHANGELOG。`--version` への応答（`verify-release` の要件）。
- リリース前の独立検証。Word と Pages での人による確認。
- 署名・notarize、`make brew`、tap、util-series への submodule 追加、util-series README のカタログ行、
  util-series CLAUDE.md にビルド事情（cgo、darwin/arm64 のみ）を 1 行、org profile README・nlink-web-site
  のカタログ・リポジトリの About、knowledge への還元、check-org。
- gem-agent・lagent への登録は運用者の機械の状態を変えるので、手順を予告し、検証の後は撤去する
  （組織 ADR-023）。

### 未解決の issue（他のプロジェクトで扱う。組織 ADR-025）

自分の計画の段にはせず、各プロジェクトに issue を立てる:

- skills-series/mcp-tactics: 新しいサーバを索引と description に加える（本文と発動の契機の 2 面）。
- skills-series: レポート作成のサポート用スキル（別 RFP）。

### 試験の方針

見た目の良し悪しでは合否を決めない。判定するのは「間違い」:

- 実際の利用に近い原稿の試験データ: gem-agent・lagent・Claude に調査レポートを書かせて集め、
  「モデルが普段書く Markdown がそのまま通る」ことを確かめる。秘密や個人の情報を含まないよう、
  試験用の題材で書かせる。
- PDF: OS の PDF 機能（PDFKit）で文字を取り出し、原稿の文字がすべて順番どおりに入っていること。
  文字・図が余白からはみ出していないことを座標で確かめる。mermaid の図はラスターなので、図が
  置かれていること・大きさ・描けないときの代替を確かめる。
- .docx: `textutil` での読み戻しは中身の照合にとどめる（Word の見え方の確認ではない）。XML の
  整形式と、使えない文字が残っていないことを確かめる。
- 仮の JSON-RPC クライアントで、起動から `render` の出力までを通す試験。
- 攻撃の形の試験: 作業ディレクトリの外を指すリンク・`..`・FIFO・巨大な寸法の画像・禁止スキームの
  リンク・出力先に置かれたリンク。
- 試験が本当に誤りを捉えるか、実装を壊して確かめる（変異で確かめる）。

### 単独でレビューできる単位

Markdown の読み取り、グラフの描画、PDF の組版、.docx の書き出し、読み書きの層は互いに依存しない部品
として作り、それぞれ単独でレビューできるようにする。

## 5. Required API Scopes / Permissions

なし。外部の API・サービス・認証情報は使わない。macOS のプライバシー許可（フルディスクアクセス等）も
不要（フォントの利用は許可の対象ではない）。原稿・画像の読み込みと出力の書き込みは、呼び出し側が指定した
作業ディレクトリの中に限る。作業ディレクトリの外で読むのは、運用者が設定ファイルに書いたもの（設定
ファイル自身とロゴ画像）だけ。

## 6. Series Placement

Series: util-series
Reason: image-forge・video-studio-mcp・voice-studio-mcp・data-toolbox-mcp と同じ「作業ディレクトリに
成果物を作る MCP サーバ」の系列。特定の外部サービスのクライアントではないため cli-series ではない。
`_wip/report-studio-mcp/` で開発を始め、公開後に util-series へ submodule として追加する。

## 7. External Platform Constraints

外部プラットフォームへの依存はない。製品側の制約:

- macOS 専用（Core Text・Core Graphics を使うため）、darwin/arm64 のみ。cgo でリンクするため対応 OS の
  下限は明示して確かめ（Phase 0）、macOS 26 の検証環境でも確認する。
- Word と Pages で同じ .docx の見え方に差が出ることがある。合否は「開けること」と「内容が欠けないこと」で
  判定し、細かな見た目の差は許容する。
- mermaid-render の上限（ノード数など）を引き継ぐ。超える図はソースで代えて警告する。
- gem-agent の呼び出しの既定の打ち切りは 60 秒。上限はこれに余裕を残して決める。
- gem-agent・lagent は大きなツール結果を切り捨てずにファイルへ退避する。警告の件数の上限は応答を
  読みやすく保つためのもので、`max_warnings` で引き上げられる。
