# 第 0 段階: 合格条件（事前登録）

> 登録: 2026-11-03（測定の前にコミットする。測定の後に条件を書き換えない）
> 根拠: RFP §4 Phase 0、組織 ADR-023

各項目は「合格」「不合格」「測れない」のどれかで記録する。不合格なら RFP の設計判断に戻る。
「測れない」は合格に読み替えず、理由と次の手を書く。測定に使う試作のコードはリポジトリの外に置き、
結果とその再現手順だけをこの文書の「結果」に書く。

## P0-1 Go から cgo で Core Text・Core Graphics を呼んで PDF を作る

`make build` と同じ条件（`CGO_ENABLED=1`、darwin/arm64）でビルドした Go のプログラムが、決まった
試験文を A4 の PDF 1 ページに組む。試験文は、ヒラギノ角ゴ W6 の見出し 1 行と、W3 の本文 1 段落
（行末に来る句読点・閉じ括弧・開き括弧と、英数字の混在を含む 600 字以上）とする。

合格の条件（すべて満たす）:

1. フォントはサブセットで埋め込まれている: PDF の各フォントの `BaseFont` が 6 文字の大文字＋`+` の
   接頭辞を持ち、`FontFile2` または `FontFile3` がある。1 ページの PDF が 100 KB 未満。
2. 文字が欠けていない: PDFKit で取り出した文字列から空白と改行を除いたものが、試験文から空白と改行を
   除いたものと一致する。
3. 禁則が効いている: Core Text が返す各行（`CTLine`）の先頭の文字が、行頭禁則の文字
   （`、。，．）」』】〕〉》！？ー・`）でない。
4. stdout を汚さない: プログラムの stdout と stderr を別々のファイルへ向けて実行し、stdout のファイルが
   0 バイトである（組版の途中でフレームワークが stdout に書かない）。
5. 対応 OS の下限が明示されている: `vtool -show-build` の `minos` が、ビルドで指定した値と一致する。
   指定する値は測定のときに決めて、この文書に記録する。

## P0-2 手書きの最小の .docx を Word と Pages で開く

標準ライブラリ（`archive/zip`、`encoding/xml` または文字列）だけで書いた .docx 1 つ。中身は、
見出しスタイル 3 段（日本語）、本文段落、3×3 の表、PNG 画像 1 つ、脚注 1 つ、目次フィールド 1 つ。

合格の条件（すべて満たす）:

1. Mac 版 Word で、修復のダイアログなしに開ける。
2. Pages で、修復や読み込みの警告なしに開ける（Pages が出す「一部の要素は変換された」類の通知は
   記録し、内容が欠けていなければ合格とする）。
3. 両方で、上の 6 要素がすべて見える（人が確認し、要素ごとの有無を記録する）。
4. `textutil -convert txt` で読み戻した本文に、段落と表の文字がすべて含まれる。

この機械には Word も Pages も入っていない（2026-11-03 確認）。用意できないアプリがある場合は
「測れない」と記録し、代わりの手段を利用者と相談する。Pages だけで合格扱いにはしない。

## P0-3 mermaid の図を PDF に埋め込む

mermaid-render の実データ（`testdata/real` の 51 個）を、A4 の本文幅（左右余白 20 mm）に表示したとき
300 dpi 相当になる倍率で描き、PNG として PDF に埋め込む。

記録すること: 図ごとの画素数、PNG の大きさ、PDF の増分。画素数の上限（mermaid-render の既定）に
当たった図の数と、そのとき倍率を下げて描けたか。

合格の条件:

1. 51 個すべてについて、図または「描けない」の結果が得られる（エンジンが止まらない・落ちない）。
2. PDF の増分の中央値が 500 KB 以下、最大が 4 MB 以下。
3. 上限に当たった図は、倍率を下げれば描ける。

## P0-4 最悪の場合の所要時間

組版エンジンはまだ無いので、Core Text と Core Graphics の素の費用を測る:
(a) 300 ページ分の本文の組版、(b) 20,000 個の矩形と 20,000 個の短い文字列の描画（大きな表とグラフの代わり）、
(c) 2,000 × 2,000 画素の PNG 50 枚のデコードと埋め込み。

合格の条件: 測った値から上限の初期値を決め、上限いっぱいの原稿の予測所要時間が 20 秒以下
（gem-agent の呼び出しの既定の打ち切り 60 秒の 3 分の 1）になる。決めた初期値をこの文書に記録する。

## P0-5 準拠する仕様の版

記録すること: CommonMark 仕様の版、GFM 仕様の版、脚注と注記ブロックの出典（GitHub Docs のページと
参照日）、Office Open XML（ECMA-376）の版と形式（Transitional）。

合格の条件: 上の 4 つがこの文書に記録され、RFP §2 の「準拠する仕様」から参照されている。

## 結果

### P0-1: 合格（2026-11-03、macOS 27.2、Go 1.27.3、Apple Silicon）

試作: cgo の C 部分で `CTFramesetter` → `CTFrameDraw` を `CGPDFContext` に描き、各 `CTLine` の先頭文字を
返す Go のプログラム（約 130 行）と、PDFKit の `PDFDocument.string` で文字を取り出す Swift の 10 行。

1. サブセット埋め込み: `AAAAAB+HiraginoSans-W6`・`AAAAAC+HiraginoSans-W3`（`CIDFontType0`、`FontFile3`）。
   PDF は 32,668 バイト。— 合格
2. 文字の欠け: 見出しと本文 600 字を、空白・改行を除いて PDFKit の取り出し結果と照合し、一致。— 合格
3. 禁則: 本文 13 行のうち、行頭禁則の文字で始まる行は 0。`CTFrameGetVisibleStringRange` で全文が枠に
   収まったことも確認。— 合格
4. stdout: stdout と stderr を別ファイルにして実行し、stdout は 0 バイト。— 合格
5. 対応 OS の下限: 26.0 に決めた（macOS 26 の検証環境があるため）。`vtool -show-build` の `minos 26.0`。
   — 合格

付記（ビルド条件の発見）: `CGO_CFLAGS`・`CGO_LDFLAGS` に `-mmacosx-version-min=26.0` を渡すだけでは、
Go の実行時の cgo 部品がビルド機の OS（27.2）向けのままで、リンカが「より新しい macOS 向けの
オブジェクト」と警告した。環境変数 `MACOSX_DEPLOYMENT_TARGET=26.0` を与えて全体をビルドし直すと
警告は 0 件になった。Makefile でこの変数を固定する。

### P0-2: 測れない（Word が無い）— Pages と代わりの LibreOffice では合格（2026-11-03）

試作: 標準ライブラリだけ（`archive/zip` と文字列）で書いた .docx。部品は `[Content_Types].xml`、`_rels/.rels`、
`docProps/core.xml`、`word/{document,styles,settings,footnotes}.xml`、`word/_rels/document.xml.rels`、
`word/media/chart.png`。フォントはヒラギノ角ゴ（`Hiragino Sans`）。目次フィールドは、フィールドを更新しない
読み手でも見えるよう、項目を書き込んだ状態で置き、`updateFields` を立てた。

| 条件 | 結果 |
|---|---|
| 1. Mac 版 Word | **測れない**: この機械に Word が無い。利用者と合意し（2026-11-03）、代わりに LibreOffice 26.8.2.2 の画面で確かめた。Word での確認は残る |
| 2. Pages（Pages Creator Studio 15.4） | 合格: 利用者の報告に修復・読み込みの警告なし |
| 3. 6 要素が見える | Pages・LibreOffice とも合格: 目次 3 行、見出し 3 段、日本語の本文、3×3 の表、画像、脚注（本文の上付き番号とページ下の脚注文）。利用者が画面の画像で確認 |
| 4. `textutil` の読み戻し | 合格: 段落と表の文字がすべて含まれる。脚注の文は読み戻されない（`textutil` の制約。条件の対象外） |

zip の整合性（`unzip -t`）と、すべての XML 部品の整形式（`xmllint --noout`）も確認した。

見えたこと（見た目の差。合否には関係しない）:

- Pages は開くときに目次を作り直し、ページ番号を見出しの直後に詰めて付けた（「調査の概要1」）。目次スタイルに
  右揃えのタブとリーダーが無いため。第 2 段階で目次スタイルにタブを定義する。
- LibreOffice は目次をフィールドの枠つきで表示し、作り直さなかった。

測定方法についての記録: この端末から `soffice --headless` で PDF に変換すると、Helvetica を含めてシステムの
フォントが一つも使われなかった（同梱の LinuxLibertineG などに置き換わる）。文書の問題ではなく実行環境の制約と
判断し、代わりの証拠には使っていない。ヘッドレス変換を試験に使う場合は、この点を先に解決する。
